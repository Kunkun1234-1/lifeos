# 商店与祈愿模块重构设计稿

> 状态：初版，等待产品审阅
> 日期：2026-07-10
> 范围：奖励商店、祈愿、`money + gold` 交易规则、库存与钱包联动
> 本轮产出：产品与交互方案、技术改造建议、原创祈愿背景图；暂不修改业务代码

---

## 0. 审阅摘要

### 0.1 已明确的产品约束

1. 系统中的交易资源统一为 `money` 和 `gold`。
2. 祈愿每次固定消耗 `160 gold`；十连固定消耗 `1600 gold`，初版不打折。
3. 每件商品必须配置一组价格：`money + gold`。
4. `money` 允许为 `0`。
5. 商店一级分类改为：
   - 虚拟商品
   - 小额实物商品：`money < 500 元`
   - 大额实物商品：本文暂按 `money >= 500 元` 理解
6. 参考图只用于提取信息架构与交互模式，不复制其角色、品牌、图标或具体美术。

### 0.2 本稿的推荐结论

- `money` 不是新的虚拟币，而是钱包中的真实预算金额，数据库继续以“分”为单位存储。
- 商店购买默认从钱包的“流动资金”扣除 `money`，同时从 `Currency.gold` 扣除 `gold`；两项必须在同一数据库事务中完成。
- 祈愿只收取 `gold`，不再支持 `fate` 或其他支付方式。
- 祈愿抽中虚拟商品后直接进入可用库存；抽中实物商品后进入“待兑现”，兑现时再从流动资金扣除该商品的 `money`，不重复扣除商品的 `gold`。
- 商品分类与稀有度分离：分类决定商店导航和预算规则，稀有度只决定祈愿概率与视觉层级。
- 大额实物商品不能静默动用储蓄池。流动资金不足时，先引导用户去钱包主动转入。

### 0.3 需要你确认的 5 个决定

| 编号 | 问题 | 本稿默认建议 |
|---|---|---|
| D1 | “大额食物商品”是否为“大额实物商品”的笔误 | 是，按大额实物商品设计 |
| D2 | 商品能否同时为 `money = 0` 且 `gold = 0` | 不允许，避免误建免费商品；如需免费权益，单独增加“赠送”来源 |
| D3 | 抽中实物后是否还要扣 `money` | 要；抽取只消耗 160 gold，实物兑现时扣 money |
| D4 | 商店 money 从哪个钱包资金池扣除 | 统一从流动资金扣除，不自动跨池 |
| D5 | 是否保留当前五星/四星保底规则 | 初版保留现有概率与保底，仅统一支付资源和界面 |

只要 D1-D5 定下来，就可以进入数据库迁移和代码实现。

## 1. 背景与目标

当前商店和祈愿已经具备奖励创建、直接兑换、入池、抽取、保底、库存记录等基础能力，但货币体系与信息架构不一致：

- 商店使用 `gold + gems`。
- 祈愿允许 `fate` 或 `gold` 二选一。
- 钱包中的真实金额没有参与商品兑换。
- 商店按稀有度分组，不符合用户按商品性质和预算寻找奖励的方式。
- 抽取、钱包和库存各自记录，缺少一个能够解释“这次奖励最终花了多少钱”的完整链路。

本次重构的目标不是再做一套普通电商，而是把“完成现实目标获得 gold”和“用预算兑现现实奖励”连成一个可控闭环：

```text
完成任务 / 习惯 / 复盘
        ↓
      获得 gold
        ↓
┌───────────────────┬───────────────────┐
│ 商店直接购买       │ 祈愿随机获得       │
│ money + gold      │ 160 gold / 次      │
└───────────────────┴───────────────────┘
        ↓                       ↓
   商品进入库存            虚拟：直接入库存
                           实物：待兑现，兑现扣 money
        └───────────────┬───────┘
                        ↓
                 使用 / 放弃 / 留存记录
```

### 1.1 产品目标

- 用户始终知道一次操作会扣多少 `money` 和 `gold`。
- 随机奖励不绕过真实预算边界。
- 商店能快速按虚拟、小额实物、大额实物浏览。
- 祈愿保留仪式感，但不使用误导性、强刺激或赌场式表达。
- 钱包流水、gold 流水、抽取记录和库存实例可追溯。

### 1.2 暂不包含

- 银行卡、微信、支付宝等真实支付渠道。
- 平台向用户收款、发货或经营第三方商品。
- 多币种商品定价。
- 限时卡池、付费充值、好友赠送、二级交易。
- 优惠券、折扣叠加和复杂库存管理。

本稿把 `money` 定义为个人钱包中的预算扣减，不是在线支付。如果未来变成面向多用户的商业化平台，需要单独进行支付、消费者权益、随机销售和实物履约合规设计。

## 2. 调研结论

### 2.1 从参考图提取的可用模式

商店参考图的优势：

- 左侧保持稳定的一级分类，右侧使用高密度商品网格。
- 余额置于右上角，用户在浏览和购买前都能看到资源状态。
- 商品卡直接展示图片、名称、限购或状态、价格，减少进入详情页才能判断的成本。
- 选中态通过边框和背景层级表达，而不是大幅改变布局。

祈愿参考图的优势：

- 大幅场景图承担氛围，主要说明和操作浮在固定安全区。
- 左侧纵向入口切换卡池，右下角集中放置单抽和十连。
- 概率规则、剩余时间、历史等辅助能力靠近主操作，但不抢主视觉。
- 货币余额保持在顶部，抽取成本显示在按钮内部。

需要避免直接照搬的部分：

- 不复制参考游戏的角色构图、logo、图标、字体与卡池命名。
- 不把祈愿设计成不断闪烁、倒计时催促或隐藏真实成本的高压消费界面。
- 本项目初版只有一个常驻奖励池，不应为了“像游戏”而制造无意义的多卡池列表。

### 2.2 商品列表研究对本项目的启发

Baymard 的商品列表研究强调，用户依赖列表中的价格、标题、缩略图和类别相关属性来判断是否值得进一步操作；缺失关键属性会迫使用户频繁打开详情。对本项目而言，商品卡必须同时露出 `money`、`gold`、商品类别和可获得状态，而不是只显示一个综合价格。

研究也区分了“分类”和“筛选”：分类用于互斥的商品范围，筛选用于在分类内组合条件。因此“虚拟 / 小额实物 / 大额实物”适合做左侧一级分类；“可购买 / 可祈愿 / 价格 / 稀有度”适合做列表顶部筛选或排序，而不应继续混成四段稀有度页面。

### 2.3 随机奖励的透明度

虽然本项目当前是个人工具而非付费盲盒平台，仍建议采用高于最低要求的透明规则：

- 在抽取前可查看完整奖池、各稀有度基础概率和保底规则。
- 每件奖品显示其在当前稀有度内的权重或计算后的实际概率。
- 抽取历史记录实际结果、消耗和触发的保底。
- 概率变更必须版本化，历史抽取保留当时的规则快照。

Apple App Review Guidelines 要求购买随机虚拟物品前披露各类物品概率；Google Play 的政策同样要求在购买前、靠近购买行为的位置清楚披露随机物品概率。中国市场监管总局的《盲盒经营行为规范指引（试行）》对经营性随机实物销售进一步提出规则、商品范围、概率、价值范围和完整记录等要求。它们不一定直接适用于当前个人工具，但共同指向同一个产品原则：**随机结果必须可理解、可追溯，不能通过后台临时改变规则。**

### 2.4 可访问性

- 价格不能只靠金色或蓝色区分，必须同时有 `money` / `gold` 图标与文字。
- 余额变化、购买成功、抽取完成应提供可被辅助技术识别的状态消息。
- 背景图上的正文需要稳定遮罩，不能把可读性押在某张图片的局部明暗上。
- 动画需支持 `prefers-reduced-motion`；跳过动画不会改变抽取结果。

## 3. 统一术语与资源模型

| 产品名 | 技术含义 | 来源 | 用途 |
|---|---|---|---|
| `money` | 钱包中的人民币预算，以分存储 | 用户记账收入与资金分配 | 商店购买、实物奖励兑现 |
| `gold` | 游戏化金币，整数 | 任务、习惯、复盘、成就等 | 商品价格、每次祈愿 160 gold |
| 商品 | 用户可直接购买或加入祈愿池的奖励定义 | 用户创建 / 系统预设 | 商店、祈愿池 |
| 库存实例 | 一次已经获得的商品权益 | 商店购买 / 祈愿结果 | 使用、兑现、放弃、追踪 |

### 3.1 资源清理策略

- 新商店和祈愿不再使用 `gems`。
- 祈愿不再使用 `fate`。
- 第一阶段可以保留数据库字段用于兼容历史记录，但新接口不再读写。
- 第二阶段确认其他模块也不再依赖后，再迁移或删除 `gems`、`fate`。
- 不建议直接把历史 `gems`、`fate` 自动兑换成 gold，除非先确定兑换比例；初版可显示一次性迁移提示。

## 4. 商店设计

### 4.1 信息架构

桌面端：左侧分类栏 + 顶部余额与工具栏 + 右侧商品网格。

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 奖励商店                                         ¥ 2,340.00  G 860 │
├──────────────┬──────────────────────────────────────────────────────┤
│ 全部商品  18 │ 虚拟商品                              [筛选] [排序] │
│              │ 12 件商品 · 直接购买后进入库存                     │
│ 虚拟商品   7 ├──────────────────────────────────────────────────────┤
│ 小额实物   8 │ ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│ 大额实物   3 │ │  商品图   │ │  商品图   │ │  商品图   │             │
│              │ │ 专注半日券│ │ 精品咖啡  │ │ 新键盘预算│             │
│              │ │ ¥0 + G120│ │ ¥32 + G80│ │¥899+G2400│             │
│              │ │  [购买]  │ │  [购买]  │ │  [余额不足]│             │
│              │ └──────────┘ └──────────┘ └──────────┘             │
│              │                                                      │
│ [管理商品]   │                                                      │
└──────────────┴──────────────────────────────────────────────────────┘
```

一级分类：

| 分类 | 规则 | 典型商品 |
|---|---|---|
| 全部商品 | 所有未归档商品 | 用于总览，不作为商品存储类别 |
| 虚拟商品 | `category = virtual`，money 可为 0 | 自由时间、免做券、娱乐时段、数字内容 |
| 小额实物商品 | `category = physical_small` 且 `money < 50000` 分 | 咖啡、餐饮、书、文具、小配件 |
| 大额实物商品 | `category = physical_large` 且 `money >= 50000` 分 | 硬件、旅行、课程、大型体验 |

分类由用户明确选择，服务端再校验金额边界。不能只根据金额在前端临时推断，否则修改价格后商品会无声跳到另一类。

### 4.2 商品卡信息优先级

卡片始终展示：

1. 商品缩略图或 emoji 回退。
2. 商品名称。
3. 双资源价格：`¥32.00 + 80 gold`，`money = 0` 时仍显示 `¥0`，明确它是零金额而不是漏配。
4. 状态：可购买、money 不足、gold 不足、两者均不足。
5. 是否加入祈愿池，使用小型状态标记，不作为主按钮。

按类别展示的补充信息：

- 虚拟商品：有效期或使用说明。
- 小额实物：预算金额、兑现说明。
- 大额实物：预算金额和“需从流动资金支付”的提示。

商品卡不直接放删除按钮。编辑、归档等低频管理动作放入商品管理模式或详情菜单，避免与购买操作并列。

### 4.3 购买流程

点击购买后打开确认对话框：

```text
购买「精品咖啡」？

本次扣除
  money  ¥32.00    流动资金剩余 ¥618.00
  gold   80        购买后剩余 340

[取消]                                      [确认购买]
```

规则：

- `money > 0`：从流动资金扣除。
- `money = 0`：不创建 0 元钱包支出流水，只记录商品价格快照为 0。
- `gold > 0`：从 gold 扣除。
- 任一余额不足则不允许部分购买，也不先扣其中一项。
- 购买成功后创建库存实例，余额和商品状态在同一响应中更新。
- 重复点击使用 idempotency key，避免多次扣款。

### 4.4 空状态与错误状态

- 分类无商品：显示“此分类还没有商品”和“新建商品”命令。
- 钱包未初始化：商品仍可浏览，但购买按钮显示“先设置钱包”。
- 月份结转未完成：money 商品暂停购买，纯 gold 商品仍可购买。
- 流动资金不足：提供“去钱包调整”入口，不自动从生活费或储蓄扣除。
- gold 不足：显示还差多少以及可获得 gold 的任务入口。
- 商品已归档：确认页刷新后提示商品已下架，不扣资源。

### 4.5 移动端

- 左侧分类改为顶部横向可滚动的分类标签。
- 商品网格为双列；320px 以下降为单列。
- 余额栏固定在页面标题下方，不遮挡系统导航。
- 购买确认使用底部抽屉；主按钮固定在抽屉底部。

## 5. 祈愿设计

### 5.1 页面结构

初版只有一个常驻池，不伪造多卡池。桌面端采用：顶部余额、左侧信息区、中右侧场景、底部操作区。

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 星轨祈愿                                      gold  3,260   [记录] │
├──────────────────────────────────────────────────────────────────────┤
│ 命轨回响                                                             │
│ 常驻奖励祈愿                    [原创星象观测台背景，焦点在中右侧]    │
│                                                                      │
│ 五星基础概率 0.6%                                                    │
│ 90 抽内必得五星                                                      │
│ 距离五星保底 34 抽                                                    │
│                                                                      │
│ [查看概率与奖池]                         [160 祈愿1次] [1600 祈愿10次]│
└──────────────────────────────────────────────────────────────────────┘
```

顶部只显示 `gold`。不再展示 `fate`、`gems` 或加号充值入口。

### 5.2 操作规则

- 单抽请求只接收 `count: 1`，服务端计算 `goldCost = 160`。
- 十连请求只接收 `count: 10`，服务端计算 `goldCost = 1600`。
- 客户端不提交价格，防止旧客户端或参数篡改改变成本。
- 抽取按钮同时显示成本和抽数。
- 余额不足时按钮禁用，并显示 `还差 N gold`。
- 点击后先完成服务端抽取并持久化结果，再播放动画。
- 动画中断、刷新或选择跳过，不影响已经持久化的结果。

### 5.3 概率与保底

初版建议保留当前规则：

| 层级 | 基础概率 | 保底 |
|---|---:|---|
| 三星 / common | 94.3% | 无 |
| 四星 / rare + epic | 5.1% | 10 抽内至少一次四星及以上 |
| 五星 / legendary | 0.6% | 74 抽开始软保底，90 抽硬保底 |

现有四星层内 `epic` 占 18%、`rare` 占 82%。这个规则也必须进入“概率详情”，不能只写总四星概率。

奖池详情需要展示：

- 每个层级的基础概率和保底说明。
- 当前保底计数。
- 当前层级内每件商品的权重和换算概率。
- 商品属于虚拟、小额实物或大额实物。
- 实物抽中后仍需兑现 `money` 的明确提示。

### 5.4 抽中后的处理

推荐使用两阶段状态，防止祈愿绕过预算：

| 商品类型 | 抽中后状态 | 后续动作 |
|---|---|---|
| 虚拟商品，money = 0 | `available` | 可直接使用 |
| 虚拟商品，money > 0 | `pending_fulfillment` | 兑现时从流动资金扣 money |
| 小额实物 | `pending_fulfillment` | 兑现时扣 money，再变为 available |
| 大额实物 | `pending_fulfillment` | 兑现时扣 money；不足则保留资格，不自动动储蓄 |

祈愿已经消耗 `160 gold`，兑现商品时不再扣商品配置中的 `gold`。商品 `gold` 价格只用于商店直接购买。

结果页必须写清：

```text
获得：机械键盘预算
祈愿消耗：160 gold
兑现所需：¥899.00（从流动资金扣除）

[稍后兑现] [现在兑现]
```

### 5.5 动画与音频

- 结果由服务端先决定，前端动画只负责表现。
- 单抽目标时长 2.5-4 秒，十连目标时长 4-6 秒；允许跳过。
- 首次进入不自动播放音频；只有用户点击祈愿后播放。
- 提供静音设置并记忆选择。
- `prefers-reduced-motion` 下使用短淡入和结果列表，不播放长飞行动画。
- 稀有度不只依靠颜色，结果同时显示星级、文字和图标。

## 6. 视觉方向与背景图

### 6.1 视觉原则

- 延续 LifeOS 的深色墨蓝、金属金、纸白与少量珊瑚色，不做单一蓝紫色界面。
- 商店偏克制和高密度，祈愿偏沉浸，但两者共享相同的余额组件、价格组件和确认对话框。
- 卡片圆角不超过 8px，选中态使用细边框与轻微明度变化。
- 背景图只承担世界观和空间感，所有可操作内容由真实 HTML 组件渲染。
- 不在生成图上绘制中文、按钮或概率，避免文字失真和后续无法维护。

## 7. 数据模型建议

### 7.1 RewardItem

```prisma
enum RewardCategory {
  virtual
  physical_small
  physical_large
}

model RewardItem {
  // existing identity and presentation fields
  category       RewardCategory @default(virtual)
  costMoneyCents Int            @default(0)
  costGold       Int            @default(0)

  // rarity remains independent from category
  tier           String         @default("common")
  inGachaPool    Boolean        @default(true)
  weight         Int            @default(1)
}
```

迁移规则：

- `costGems` 停止使用，新增 `costMoneyCents`。
- 历史商品的 `costMoneyCents` 初始设为 0，等待用户补充。
- 历史商品根据描述无法可靠判断实物/虚拟，统一迁移为 `virtual`，在管理页提供一次性分类校正清单。
- 保留 `tier`，因为祈愿仍需要稀有度与保底。

服务端校验：

```text
costMoneyCents >= 0
costGold >= 0
costMoneyCents > 0 OR costGold > 0
virtual: 无金额上限
physical_small: 0 <= costMoneyCents < 50000
physical_large: costMoneyCents >= 50000
weight >= 1
```

### 7.2 RewardRedemption

库存实例必须保存价格快照，不能读取商品当前价格解释历史：

```prisma
model RewardRedemption {
  acquisitionSource String   // store | gacha
  status            String   // pending_fulfillment | available | used | discarded
  costMoneyCents    Int      @default(0)
  costGold          Int      @default(0)
  walletTransactionId String?
  fulfilledAt       DateTime?
}
```

快照含义：

- 商店来源：`costMoneyCents` 和 `costGold` 都是实际扣除值。
- 祈愿来源：`costGold = 160` 表示本次抽取成本的归因值；`costMoneyCents` 在兑现时记录实际扣除。
- 十连一次请求的 1600 gold 需要在 `GachaPullBatch` 或等价批次表中保存，单件归因可保持每抽 160。

### 7.3 GachaPull

当前表只有 `fateSpent`，无法正确记录 gold 抽取。建议改为：

```prisma
model GachaPull {
  id              String   @id @default(cuid())
  batchId         String
  userId          String
  rewardId        String?
  tier            String
  goldSpent       Int      @default(160)
  pity            String?
  rulesVersion    String
  probabilityBps  Int?
  pulledAt        DateTime @default(now())
}
```

可新增 `GachaPullBatch` 保存请求级幂等键、抽数、总成本和客户端动画恢复信息。

### 7.4 钱包流水关联

商店购买或实物兑现产生一条 `expense`：

```text
type = expense
necessity = optional
sourcePoolType = flexible
amountCents = 商品实际 money
counterparty = 商品名称
note = store purchase / gacha fulfillment
```

建议给钱包流水增加可选的 `referenceType + referenceId`，或在 `RewardRedemption` 上保存 `walletTransactionId`，使库存详情可以跳转到对应流水。

## 8. API 合约建议

### 8.1 商店列表

```http
GET /api/store/products?category=physical_small&affordability=all&sort=recommended
```

返回商品、余额摘要和是否可购买：

```json
{
  "balances": {
    "moneyAvailableCents": 65000,
    "gold": 420
  },
  "items": [
    {
      "id": "reward_1",
      "name": "精品咖啡",
      "category": "physical_small",
      "cost": { "moneyCents": 3200, "gold": 80 },
      "affordability": {
        "canPurchase": true,
        "moneyShortfallCents": 0,
        "goldShortfall": 0
      }
    }
  ]
}
```

### 8.2 商店购买

```http
POST /api/store/products/:id/purchase
Idempotency-Key: <uuid>
```

请求不携带价格。服务端读取当前商品价格，并在一个事务中：

1. 校验商品仍可购买。
2. 条件扣减流动资金。
3. 条件扣减 gold。
4. 创建钱包流水与 allocation。
5. 创建库存实例和价格快照。
6. 增加商品已兑次数。

### 8.3 祈愿状态

```http
GET /api/wish
```

返回：gold 余额、概率版本、保底计数、奖池商品、最近记录、单抽成本 `160`。

### 8.4 祈愿抽取

```http
POST /api/wish/pull
Idempotency-Key: <uuid>
Content-Type: application/json

{ "count": 1 }
```

只接受 `1 | 10`。不接受 `currency` 或客户端价格。

## 9. 一致性与风险控制

### 9.1 当前实现的关键风险

现有祈愿接口逐抽创建记录和库存，最后才扣货币与更新保底。十连过程中如果请求失败，可能已经获得部分商品但尚未扣除 gold；并发请求也可能同时通过余额检查。

重构必须将以下操作放入一个交互式数据库事务：

- 条件扣减 gold。
- 读取并更新保底计数。
- 生成所有结果。
- 创建抽取批次和逐抽记录。
- 创建库存实例。

商店购买同样需要对流动资金和 gold 使用条件更新，例如余额 `gte` 扣款值；不能先查询余额、再无条件 decrement。

### 9.2 幂等与恢复

- 每次购买和祈愿必须带幂等键。
- 相同用户和幂等键只返回第一次结果，不再次扣款。
- 前端动画开始前保存 `batchId`。
- 刷新页面后可根据 `batchId` 恢复结果页，不重新抽取。

### 9.3 概率实现

- 概率配置集中在服务端，避免页面文案与算法常量分离。
- 每次抽取保存 `rulesVersion`。
- 空层级不能像当前实现一样静默降级到其他层级，否则展示的概率与实际结果不一致。
- 发布前要求每个启用层级至少有一件商品；否则禁止开启祈愿池并显示配置错误。
- 增加可重复的统计测试，验证百万级模拟下概率和保底边界在容差内。

## 11. 验收标准

### 商店

- 左侧可切换虚拟、小额实物、大额实物，数量与列表一致。
- 每张商品卡同时显示 money 和 gold，money 为 0 时仍明确显示。
- 小额实物必须小于 500 元，大额实物必须大于等于 500 元。
- 购买时 money 与 gold 要么都成功扣除，要么都不扣除。
- money 支出生成流动资金流水并可从库存追溯。
- 连续双击或重放请求不会重复扣款。

### 祈愿

- 单抽只消耗 160 gold，十连只消耗 1600 gold。
- API 不再接受 fate 或客户端提交的价格。
- 抽取前可查看完整概率、奖池和保底规则。
- 结果在动画前持久化，刷新不会改变结果或再次扣款。
- 十连失败不会出现部分发奖、未扣 gold 的状态。
- 抽中实物进入待兑现，兑现时才扣 money。
- 动画可跳过并支持 reduced motion。

### 响应式与可访问性

- 1440×900、1280×720、390×844、360×800 下无文字或按钮重叠。
- 背景图加载失败时内容仍可阅读和操作。
- 余额变化和交易结果有程序可识别的状态消息。
- 价格和稀有度不只使用颜色表达。

## 13. 代码现状对照

| 现状 | 目标 | 影响范围 |
|---|---|---|
| `RewardItem.costGold + costGems` | `costMoneyCents + costGold` | Prisma、DTO、校验、种子、商店、库存 |
| 商店按 tier 分区 | 商店按 category 分类，tier 仅用于祈愿 | `src/app/rewards/page.tsx` |
| 祈愿支持 fate / gold | 只支持 gold，160 / 次 | gacha 页面、hook、两个 API route |
| `GachaPull` 只存 `fateSpent` | 存 batch、goldSpent、rulesVersion | Prisma 与迁移 |
| 逐抽写库，最后扣款 | 单事务先锁定成本并写入全部结果 | `apps/api/.../gacha/pull/route.ts` |
| 抽中商品直接 available | 实物先 pending_fulfillment | 库存类型、页面、API |
| 钱包和奖励无关联 | money 支出与 redemption 可互相追溯 | WalletTransaction / RewardRedemption |

建议在实现时把页面路由从 `/rewards` 和 `/gacha` 保留为兼容入口，导航文案改成“商店”和“祈愿”；等外部链接稳定后，再决定是否迁移到 `/store` 与 `/wish`。
