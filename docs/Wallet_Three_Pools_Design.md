# 钱包三资金池重构方案

> 状态：关键产品决定已确认，进入实现
> 范围：钱包的信息架构、资金分配规则、流水规则与前端界面
> 本文暂不进入数据库迁移和代码实现

---

## 0. 方案结论

本次重构的核心，是把钱包从“钱放在哪个真实账户”改成“这笔钱准备拿来做什么”。

取消现金、银行卡、支付钱包、信用卡等账户分区，钱包只保留三个资金池：

1. **每月生活费**：保障当月日常生活的必需开支。
2. **储蓄池**：沉淀长期资金，默认不直接消费。
3. **流动资金池**：承担非必需消费、临时支出和可自由调度资金。

新收入进入钱包时，采用以下顺序：

```text
收入
  ↓
补足本月生活费
  ↓
剩余金额的 50% → 储蓄池
剩余金额的 50% → 流动资金池
```

因此，对当前设计的理解是：**是的，先补足用户设定的本月生活费，之后的剩余金额再按 50% / 50% 分别进入储蓄池和流动资金池。** 这里的 50% 是“补足生活费后的余额”的 50%，不是整笔收入的 50%。

---

## 1. 重构目标

### 1.1 要解决的问题

当前钱包以真实账户为中心，需要用户理解账户、资产、负债、转账、分类和预算等多个概念。它适合记账，但不能直接回答更重要的问题：

- 这个月的钱够不够生活？
- 我真正存下了多少钱？
- 我现在有多少钱可以灵活使用？
- 这笔消费到底是不是必须的？

三资金池方案通过减少分类和账户管理，把钱包变成一个可执行的资金分配系统，而不仅是历史账本。

### 1.2 产品目标

- 用户一眼看懂自己的钱在三个用途中的分布。
- 收入记录后自动生成清晰、可确认的分配方案。
- 用户只需判断支出“必须”或“非必须”，降低记账成本。
- 储蓄与可消费资金形成心理隔离，减少无意识动用储蓄。
- 保留完整流水，让每次自动分配和手动调整都可追溯。

### 1.3 暂不包含

- 银行卡、微信、支付宝等真实账户余额同步。
- 信用卡、债务、投资收益和净资产管理。
- 多币种换算。
- 复杂消费分类、分项预算和报表。

这意味着新版首先是“资金规划钱包”，不是完整的个人资产负债表。若未来仍需要真实账户对账，应作为独立的高级能力，而不重新占据钱包主界面。

## 2. 三个资金池的定义

| 资金池 | 用途 | 默认入金规则 | 默认出金规则 |
|---|---|---|---|
| 每月生活费 | 房租、吃饭、通勤、水电等当月必须支出 | 每笔收入优先补足用户设定的本月目标 | “必须”支出默认从这里扣除 |
| 储蓄池 | 长期储备、未来目标、应急金 | 生活费补足后，剩余金额的 50% | 不允许普通支出直接扣除，需先手动转出 |
| 流动资金池 | 娱乐、购物、临时支出和自由调度 | 生活费补足后，剩余金额的 50% | “非必须”支出默认从这里扣除 |

### 2.1 基本约束

- 三个池子的余额之和等于当前钱包总额。
- 资金池是用途分配，不对应某张银行卡或某个支付软件。
- 池间移动不会改变钱包总额，但必须产生一条“资金调整”流水。
- 储蓄池默认受保护，避免普通消费无感扣除。
- 所有金额以分为最小单位计算，避免小数误差。

### 2.2 命名建议

界面建议使用更短、更容易扫描的名称：

- `每月生活费`
- `储蓄`
- `流动资金`

文档和技术模型中可继续使用“生活开支池、储蓄池、流动资金池”。“资金储蓄值”建议统一改为“储蓄池”。

## 3. 本月生活费目标

“生活费是否充足”不由系统擅自判断，而由用户通过金额目标决定。

### 3.1 首次设置

首次进入新版钱包时，引导用户完成两项输入：

1. 当前可分配的总金额。
2. 本月希望保留的生活费金额。

系统将生活费目标作为当月配置保存。目标不是消费上限，而是用户希望生活费池在补充后达到的可用金额。

### 3.2 每月设置

- 每个自然月拥有独立的生活费目标。
- 新月份默认沿用上个月的目标，用户可修改。
- 首页始终显示“当前可用 / 本月目标 / 尚缺金额”。
- 用户可在任意一笔收入分配前临时修改目标。

### 3.3 用户最终确认

系统可以根据目标自动计算，但不能在没有确认的情况下替用户做不可见的资金分配。记录收入时展示分配预览，用户确认后再入账。

预览中提供：

- 本月生活费目标输入框。
- “本月生活费已足够”开关；打开后，本笔收入不再补生活费。
- 三个池子将获得的金额。
- 调整入口，用于本次手动修改分配结果。

手动调整时，三个分配金额之和必须等于本次收入。

## 4. 收入分配规则

### 4.1 标准算法

设：

- `I`：本次收入。
- `T`：用户设定的本月生活费目标。
- `L`：收入入账前，生活费池的当前可用余额。
- `G = max(T - L, 0)`：生活费缺口。
- `A = min(I, G)`：本次补入生活费的金额。
- `R = I - A`：补足生活费后的剩余金额。

则：

```text
生活费入账 = A
储蓄入账   = R × 50%
流动资金入账 = R - 储蓄入账
```

若遇到无法平均分配的 1 分钱，默认将其放入流动资金池，保证总额严格一致。

### 4.2 示例一：收入足以补足生活费

```text
本月生活费目标：6,000 元
当前生活费余额：2,000 元
本次收入：10,000 元

先补生活费：4,000 元
剩余：6,000 元
储蓄：3,000 元
流动资金：3,000 元
```

### 4.3 示例二：生活费已经充足

```text
本月生活费目标：6,000 元
当前生活费余额：6,500 元
本次收入：5,000 元

生活费：0 元
储蓄：2,500 元
流动资金：2,500 元
```

### 4.4 示例三：收入不足以补足生活费

```text
本月生活费目标：6,000 元
当前生活费余额：2,000 元
本次收入：3,000 元

生活费：3,000 元
储蓄：0 元
流动资金：0 元
收入完成后生活费仍缺 1,000 元
```

### 4.5 分配比例

50% / 50% 是默认值，第一版即允许用户修改。用户调整储蓄比例后，流动资金比例自动使用其补数，二者之和始终为 100%。新比例只影响后续收入，不重算历史流水。

## 5. 支出与流水规则

### 5.1 流水类型

保留三类用户行为，但改变其含义：

| 类型 | 用户填写 | 系统行为 |
|---|---|---|
| 收入 | 金额、来源、日期、备注 | 按入金规则分配到三个池子 |
| 支出 | 金额、必须/非必须、日期、对象、备注 | 根据必要性选择默认扣款池 |
| 资金调整 | 金额、转出池、转入池、备注 | 只改变池子分布，不改变钱包总额 |

“收入自动分配”在流水详情中显示为一条收入及其三个分配明细，不拆成三条互不相关的收入。

### 5.2 支出分类

消费分类只保留两个：

- **必须**：维持正常生活所需的支出，默认从每月生活费扣除。
- **非必须**：可以推迟、替代或不发生的支出，默认从流动资金扣除。

“必须 / 非必须”只适用于支出。收入不要求选择这项分类，资金调整也不需要分类。

### 5.3 余额不足

当默认资金池余额不足时，不建议自动跨池扣款，否则三个池子的心理边界会失效。界面应暂停提交并让用户主动选择：

- 减少本次支出金额。
- 从流动资金转入生活费。
- 将储蓄转出到生活费或流动资金，并显示二次确认。
- 取消记录。

储蓄转出提示文案应保持中性，例如：“这会减少已储蓄金额”，不使用羞辱或过度警告式表达。

### 5.4 编辑、删除与退款

- 删除流水必须同时回滚其对各资金池的影响。
- 编辑收入金额后，重新展示分配预览，不能静默重算。
- 收入、支出和资金池互转均可编辑；保存时先回滚原资金变化，再按修改后的内容重新入账。
- 退款作为独立反向支出记录，第一版仅支持全额退款，并退回原支出的资金池。
- 已退款支出和退款流水不可编辑；删除原支出前必须先删除对应退款流水。
- 每条流水保存分配快照，避免以后修改默认比例时改变历史结果。

## 6. 月份切换规则

月末未用完的生活费默认转入流动资金，但必须由用户人工确认，不在后台自动发生。

新月份第一次进入钱包时显示“处理上月生活费结余”，默认操作为将生活费池的当前余额全部转入流动资金。完成结转前，暂停记录新流水，避免新月份收入已经补足生活费后再错误结转。

除月末结转外，三个资金池在任何时间都允许人工互转。池间转账必须生成资金调整流水；从储蓄转出时额外显示确认提示。

## 7. 前端信息架构

### 7.1 页面名称

现有“人生资产 / Assets Ledger”建议改为：

- 中文主标题：`我的钱包`
- 英文副标题：`Money Pools`

页面不再展示“新账户”、资产、负债、账户数量和账户列表。

### 7.2 桌面端结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 我的钱包                                      [记收入] [记支出] │
│ 总金额 ¥18,500                 2026 年 7 月  [设置]             │
├──────────────────────────────────────────────────────────────┤
│ 每月生活费                  储蓄                 流动资金       │
│ ¥4,200 / ¥6,000            ¥9,300               ¥5,000        │
│ 还需补足 ¥1,800             本月新增 ¥2,000       可自由使用     │
│ [进度条]                                                       │
├──────────────────────────────────────────────────────────────┤
│ 本月概览                                                     │
│ 必须支出 ¥1,800    非必须支出 ¥620    本月收入 ¥8,000          │
├──────────────────────────────────────────────────────────────┤
│ 流水                                           [全部] [筛选]   │
│ 07-10  支出 · 必须 · 房租       每月生活费       -¥1,500       │
│ 07-08  收入 · 工资              自动分配         +¥8,000       │
│         生活费 +¥2,000  储蓄 +¥3,000  流动 +¥3,000            │
└──────────────────────────────────────────────────────────────┘
```

三个资金池是首屏的主要视觉对象，使用并列区块而不是隐藏在侧栏。每个池子展示的信息应有差异，不做三个完全相同的装饰卡片：

- 每月生活费：当前余额、目标、缺口和进度。
- 储蓄：当前余额、本月净增加额。
- 流动资金：当前余额、本月非必须支出。

### 7.3 移动端结构

- 顶部显示钱包总额和月份。
- 三个资金池纵向排列，生活费池优先。
- 底部固定两个主要操作：记收入、记支出。
- 流水使用列表，不使用需要横向滚动的表格。
- 筛选器放入底部抽屉，避免占用首屏空间。

### 7.4 记收入流程

建议使用两步弹窗或移动端底部抽屉：

**第一步：填写收入**

- 金额，必填。
- 来源，可选，例如工资、退款、兼职。
- 日期，默认今天。
- 备注，可选。

**第二步：确认分配**

```text
本次收入 ¥10,000

本月生活费目标  [ ¥6,000 ]
当前还缺 ¥4,000

分配结果
每月生活费       ¥4,000
储蓄             ¥3,000
流动资金         ¥3,000

[调整分配]                         [确认入账]
```

确认按钮上方必须显示“合计 ¥10,000”，修改任一金额后实时校验总和。

### 7.5 记支出流程

支出表单应尽量短：

1. 输入金额。
2. 使用分段选择器选择“必须 / 非必须”。
3. 系统立即显示将从哪个池子扣除。
4. 补充对象、日期、备注后确认。

```text
支出金额  [ ¥280 ]

[必须] [非必须]
将从“每月生活费”扣除，扣除后剩余 ¥3,920

对象      [ 超市 ]
日期      [ 2026-07-10 ]
备注      [        ]

                              [确认支出]
```

不要再展示旧版的账户选择和多级分类选择。

### 7.6 流水列表与详情

默认按时间倒序排列，支持以下筛选：

- 类型：全部、收入、支出、退款、资金调整。
- 支出性质：必须、非必须。
- 资金池：生活费、储蓄、流动资金。
- 月份。

筛选条件可以组合使用。收入行显示实际分配明细，退款行标记退回的原资金池，资金调整使用双向箭头并明确显示“储蓄 → 流动资金”，避免被误解为收入或支出。

### 7.7 设置入口

钱包设置首版只保留必要项目：

- 本月生活费目标。
- 收入剩余分配比例，默认 50% / 50%，第一版允许修改。
- 月初是否沿用上月目标。
- 初始资金分配。

## 8. 关键状态与反馈

### 8.1 空状态

新用户不要看到三个全为 0 的池子和空流水表。应直接进入初始化流程：

1. 填写当前可分配总额。
2. 填写本月生活费目标。
3. 自行分配当前总额到三个池子。
4. 确认并进入钱包首页。

### 8.2 生活费不足

当生活费低于目标时，突出显示缺口，但不使用红色错误态。它是待补足状态，不一定是风险或失败。

### 8.3 达成储蓄

收入分配完成后，使用短暂的数值变化反馈即可，例如“本次已存下 ¥3,000”。不增加抽奖或过强动画，避免严肃财务行为被娱乐化。

### 8.4 错误与恢复

- 表单提交期间禁用重复提交。
- 自动分配应由服务端以事务完成，不能出现只更新部分资金池的状态。
- 请求失败时保留用户已经填写的内容。
- 删除和储蓄转出需要确认，并说明具体影响金额。

## 9. 数据与技术设计建议

### 9.1 核心数据对象

建议至少包含以下概念：

| 对象 | 关键字段 |
|---|---|
| `WalletPool` | 用户、池类型、当前余额、币种 |
| `WalletMonthlyPlan` | 用户、月份、生活费目标、储蓄比例、是否沿用上月、结转状态 |
| `WalletTransaction` | 类型、金额、支出性质、来源/对象、退款关联、日期、备注 |
| `WalletAllocation` | 所属流水、资金池、变动金额、变动后余额 |

一条收入对应一条 `WalletTransaction` 和一到三条 `WalletAllocation`。这样既能把收入作为一个整体展示，也能准确追踪每个池子的变化。

### 9.2 一致性要求

- 创建、编辑、删除流水与池余额更新必须在同一个数据库事务中完成。
- 服务端必须重新计算并校验分配总额，不能只相信前端结果。
- 任意时刻都应满足：收入分配合计等于收入金额。
- 历史流水保存当时的生活费目标和分配比例快照。
- 支出必须记录实际扣款池，即使它与默认池不同。

### 9.3 从现有账户模型迁移

当前系统已经存在真实账户、分类和流水，不能直接删除后重新计数。建议分阶段迁移：

1. **冻结旧模型写入**：发布新钱包后，旧账户和旧分类不再新增。
2. **旧数据清零**：旧账户、负债、信用卡、投资、分类和流水均不计入新版钱包，不计算旧账户余额之和。
3. **用户做初始分池**：将确认金额分到三个新池子。
4. **不迁移旧流水**：新版从初始化时刻重新开始记录，不强行推断旧记录的必须/非必须属性。
5. **新流水使用新模型**：迁移日之后的收入和支出全部进入三池规则。

不建议把旧消费分类自动映射为必须/非必须，因为相同类别对不同用户可能有完全不同的必要性。

## 10. 验收标准

### 10.1 核心规则

- 用户可以为每个月设置生活费目标。
- 新收入优先补足生活费，余额再按 50% / 50% 分配。
- 收入不足以补足生活费时，不产生储蓄和流动资金分配。
- 生活费已足够时，收入全部按 50% / 50% 分配。
- 每次入账前用户都能看见并确认分配结果。
- 所有池余额变化可由流水完整解释。

### 10.2 支出体验

- 支出只需要选择必须或非必须。
- 必须支出默认扣生活费，非必须支出默认扣流动资金。
- 普通支出不会自动动用储蓄。
- 余额不足时必须由用户明确决定如何处理。

### 10.3 界面体验

- 主界面不再出现真实账户分区和“新账户”入口。
- 首屏可同时看到三个池子的余额与生活费缺口。
- 桌面和移动端都无需横向滚动即可完成主要操作。
- 收入分配明细和池间调整能在流水中被清晰识别。

## 11. 已确认的产品决定

1. 三个池子使用“每月生活费 / 储蓄 / 流动资金”。
2. 生活费是否充足按当前剩余余额判断；消费后遇到新收入时可能再次补足。
3. 月末生活费余额默认人工转入流动资金，三个池子均可人工互转。
4. 收入剩余部分默认按 50% / 50% 分配，第一版允许用户修改比例。
5. 必须支出超过生活费余额时允许直接使用流动资金，但必须显示警告并由用户确认。
6. 储蓄池第一版不拆分多个储蓄目标。
7. 原有负债、信用卡和投资账户退出产品，旧财务数据清零。
8. 旧账户负余额及其他旧账户余额均不计入新版钱包的可分配总额。

## 12. 实现与测试状态

截至 2026-07-10，第 11 节确认的 8 项产品决定及本轮 4 项扩展交互均已实现：

1. 单笔收入支持“本月生活费已足够”开关，并可手动调整三个资金池的分配金额；服务端校验三项之和必须等于收入金额。
